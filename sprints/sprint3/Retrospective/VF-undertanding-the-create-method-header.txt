This is a static factory method — a common alternative to using a constructor directly.
Normally you'd instantiate an object like new DashboardCalculations(...), but here you call DashboardCalculations.create(user, goal) instead. The method is static because it doesn't belong to any instance — it exists at the class level specifically to produce instances.
The reason to prefer this pattern over a plain constructor comes down to what you can do before handing back the object:

Validation — the two null checks at the top would be awkward or repetitive in a constructor, and a constructor can't refuse to produce an object as cleanly (it would have to throw mid-construction). Here, you gate entry before anything is built.
Computation — consumedAmount and targetAmount are derived values. The factory method calls helper methods to calculate them, then passes the results into the private constructor. This keeps the constructor simple and dumb.
Readable intent — create(user, goal) communicates more clearly than new DashboardCalculations(user, goal) would, especially if the constructor signature would otherwise be confusing.

The constructor being called at the bottom is almost certainly private, which enforces that the only way to get a DashboardCalculations is through this method. That's the full pattern.
One honest critique: the method name create is pretty generic. Something like forUser or calculate would tell you more about what it's actually doing.

Here's how to use it:

Right-click your test class → Coverage As → JUnit Test
After it runs, your source files will be highlighted:

🟢 Green — line was hit
🔴 Red — line was never hit
🟡 Yellow — branch was only partially hit (e.g. an if where only one branch was covered)



To see which specific test hit a line, that's harder — EclEmma doesn't show that out of the box. It only shows aggregate coverage across all tests.
If you need per-test line attribution, your options are basically:

Run tests individually and check coverage each time — tedious but straightforward
Add a breakpoint on the line and run in debug mode, which will tell you exactly which test tripped it

EclEmma should come bundled with modern Eclipse — if you don't see "Coverage As" in the right-click menu, you may need to install it via Help → Eclipse Marketplace → search "EclEmma".

When Eclipse hits a breakpoint during a test run, look at the Debug view (usually top-left when it switches to Debug perspective). You'll see a stack trace like:
Thread [main]
  YourClass.create(User, PrimaryGoal)  line: 12
  HomeDashboardVMTest.testSomething()  line: 45   ← this is your test
  ...JUnit runner frames below...
The stack trace shows the full call chain, so you can see exactly which test method triggered the execution that landed on your breakpoint.
If the Debug view isn't visible, you can get to it via Window → Show View → Debug.
